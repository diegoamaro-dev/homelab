## 1. Naming hygiene — non-mixing rule

> **Hard rule.** `amarolab.es` is for **AMAROLAB** services.
> `guardiancloud.app` is for **Guardian Cloud**. Do not host an
> AMAROLAB service under `*.guardiancloud.app`, and do not host a
> Guardian Cloud service under `*.amarolab.es`.

Rationale:

- Guardian Cloud is an **independent project** that happens to be
  hosted on AMAROLAB infrastructure. Its naming, branding, and
  customer-facing surface must remain visibly separate from the
  AMAROLAB ecosystem.
- AMAROLAB principle from
  [`../../01_architecture/amarolab_architecture.md`](../../01_architecture/amarolab_architecture.md)
  §"Guardian Cloud": *"Guardian Cloud is not part of AURORA. Its
  internal architecture and roadmap are tracked by the Guardian
  Cloud project."*
- Operational principle from
  [`../../07_operations/lessons_learned.md`](../../07_operations/lessons_learned.md)
  §"Lesson 014": *"Production and experimentation must remain
  separate. Guardian Cloud is production."*

Concretely:

| Domain | Owns | Notes |
|---|---|---|
| `amarolab.es` | AMAROLAB ecosystem (HA, Open WebUI, Qdrant, docs, status) | Public DNS now managed in Cloudflare |
| `guardiancloud.app` | Guardian Cloud (`app.`, `api.`) | **Unchanged.** Continues on the existing tunnel. |

The existing Cloudflare Tunnel (UUID
`1a0df79d-18f0-4fd0-ba16-e51739a54c30`, audited in
[`./cloudflared_audit_2026-06-17.md`](./cloudflared_audit_2026-06-17.md))
currently serves only `guardiancloud.app` hostnames. Adding
`amarolab.es` hostnames to the same tunnel is the **planned**
posture — it keeps the operational surface narrow (one connector,
one set of edge connections to monitor) while keeping the public
hostnames and the public-facing branding cleanly separated.

## 3. Production target — `ha.amarolab.es`

### 3.1 Why this exists

`ha.amarolab.es` is the **trusted HTTPS origin** the Phase D-1.5
apply log needs to unblock G-D4. Chrome refuses
`MediaDevices.getUserMedia()` on `http://192.168.178.79:8123`
because the origin is not a Secure Context; an HTTPS hostname
served via Cloudflare resolves that.

### 3.2 DNS record (planned)

| Type | Name | Content | Proxy | TTL |
|---|---|---|---|---|
| `CNAME` | `ha` | `<tunnel UUID>.cfargotunnel.com` (the canonical Cloudflare Tunnel target — exact form generated by the Zero Trust dashboard when the public hostname is created) | **Proxied** (orange cloud) | Auto |

### 3.3 Tunnel ingress (planned, append before catch-all)

Inserted **before** the existing `http_status:404` catch-all in
the tunnel ingress (token-managed; edited in the Cloudflare Zero
Trust dashboard):

```jsonc
{
  "hostname": "ha.amarolab.es",
  "originRequest": {
    "noTLSVerify": false
    // additional originRequest options (connectTimeout etc.) to be
    // confirmed during the actual cutover, not now.
  },
  "service": "http://homeassistant:8123"
  // host-IP fallback for the first cutover (no Docker-network
  // change yet): "http://192.168.178.79:8123"
}
```

The **service** value depends on the network decision in §6
("`cloudflared` on `ai-local_default` vs. host-IP routing"). Until
that decision is closed, the safe first-cut form is the host IP
`http://192.168.178.79:8123` — it works regardless of Docker
network topology and mirrors the existing pattern used for
`api.guardiancloud.app`.

### 3.4 HA configuration changes that must accompany activation

These are **not** applied in D-1.5; they are listed here for the
cutover runbook.

| Setting | Reason |
|---|---|
| `http.use_x_forwarded_for: true` | Forwarded-for header from Cloudflare |
| `http.trusted_proxies:` add Docker bridge subnets the tunnel will egress from (e.g., `172.24.0.0/16`, and `172.18.0.0/16` if `cloudflared` joins `ai-local_default`) | Required for `use_x_forwarded_for` to take effect |
| Allowed external URL | Add `https://ha.amarolab.es` so HA does not reject the origin |

## 6. Open architectural decisions

### 6.1 Network attachment for `cloudflared`

The audit (§4 of
[`./cloudflared_audit_2026-06-17.md`](./cloudflared_audit_2026-06-17.md))
established that `cloudflared` cannot reach `openwebui` /
`qdrant` by Docker DNS today because it is not on
`ai-local_default`.

Two options:

| Option | Pros | Cons |
|---|---|---|
| **A — attach `cloudflared` to `ai-local_default`** as a second network | Clean Docker-DNS resolution; no host-IP literals in ingress; no host ports needed on `openwebui` / `qdrant` long-term | Requires touching the `cloudflared` compose stack; expands cloudflared's reachable surface to all containers on `ai-local_default` (mitigated because cloudflared is egress-only and only sees what the tunnel ingress specifies) |
| **B — keep `cloudflared` isolated; route via host IP** | No Docker compose changes for cloudflared | Hardcodes `192.168.178.79` into the ingress; relies on `openwebui` continuing to publish `:3000` to the host; harder to evolve |

**Recommendation:** Option **A**. Defer the final decision until
zone activation completes; document the chosen option in the
post-activation apply log.

### 6.2 Cloudflare Access policy on `qdrant.`

`qdrant.amarolab.es` must **not** go live without an Access
policy. This is a hard prerequisite. Tracked here so it is not
forgotten at activation time.

### 6.3 Tunnel token rotation (R-01)

Sequenced **after** zone activation and ingress migration so that
ingress edits and credential rotation do not compound in the same
maintenance window. R-01 remains the only open security
remediation per
[`../../06_security/security-risks-2026-06-13.md`](../../06_security/security-risks-2026-06-13.md)
and is referenced in
[`../../00_overview/CURRENT_STATE.md`](../../00_overview/CURRENT_STATE.md)
§"Known pending items".

### 6.4 `cloudflared` version bump

`2026.3.0` → `2026.6.0` (latest upstream warning observed in
audit). Sequenced **after** ingress migration and **after** R-01
rotation — config, credentials, and binary should not change in
the same window.

1. Confirm Cloudflare zone for `amarolab.es` is active.
2. Decide §6.1 (network attachment for `cloudflared`); apply the
   chosen option and re-verify Docker DNS from inside the
   `cloudflared` container.

   `Updated to new configuration … version=N+1` line; confirm.

   manually if dashboard automation is disabled).

   a Chromium Secure Context (DevTools → Application → "Secure

   the workstation browser; promote
   `09_logs/2026-06-17_phaseD_voice_pipeline.md` from DRAFT to
   non-draft and create `09_logs/2026-MM-DD_phaseD_gate_gd4_applied.md`.
8. Repeat steps 3–6 for `ai.amarolab.es` (target `openwebui`).
9. Sequence R-01 tunnel token rotation.
10. Sequence `cloudflared` version bump.
