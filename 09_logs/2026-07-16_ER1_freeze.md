## 2. What was frozen

The **Entity Resolution Layer** — deterministic natural-language → `entity_id` resolution,
plus **mandatory write verification (ER-1-C1)**. Ten decisions ratified: **D-ER-1…10**
(register in the spec §3).

ER-1 **amends no frozen decision**. AD-21 §7 already states the intent ("real entity_ids live
in `binding`; Aurora can answer 'that isn't an entity I model' instead of inventing ids");
ER-1 implements it. **No architecture amendment.**

## 3. Evidence base (real, re-verified at freeze)

Live `amarolab-audit.log{,.1}` (2026-06-16 → 2026-07-14) shows **13 unverified writes across
7 non-existent entity ids reported as successful** (`result_code:"ok"`). Every one of those 7
ids was re-probed against `/api/states` on **2026-07-16** and returned **HTTP 404 — does not
exist**; the 4 real targets (`switch.impresora_3d`, `cover.toldo`, `sun.sun`,
`binary_sensor.sensor_puerta_principal_contact`) all exist. Full table: spec §1.

Two evidence findings shaped the design and are recorded because they correct or sharpen the
2026-07-14 defect record:

1. **The failure requires a live HA domain.** HA returns 200 + empty list only when the
   service exists and the entity does not. `light.kitchen` never reached HA (input-validation
   failure) and is therefore **not** evidence of this defect — the true corpus is the
   `switch.*` / `automation.*` / `cover.awning` calls above.
2. **The audit log cannot distinguish a real actuation from an unverified write** —
   `switch.impresora_3d → ok` and `switch.3d_printer → ok` are byte-identical lines.
   Restoring that distinction was made an acceptance condition (G-ER-3b), not a side effect.

**The read path is not defective** — `ha_get_state` already answers `not_found` for invented
ids. ER-1's read-side change is purely additive, which is why reads cut over before writes.

## 4. Decisions of record (rationale for the non-obvious ones)

- **D-ER-9 — no write-surface restriction (operator-directed).** An earlier draft proposed a
  *closed* write lookup (writes only to modelled entities). **Rejected by the operator**: the
  World Model must improve natural-language resolution, **not** become the mandatory source of
  every writable entity. A syntactically valid `entity_id` follows the current path exactly as
  today; D-12 remains the sole authorization authority. Any stronger restriction is a **future
  architectural decision**, explicitly out of ER-1 scope.
  - **Consequence, accepted:** ER-1 does **not** prevent a pointless HA call for an invented
    id; it prevents the **false success claim**. The write still reaches HA, HA does nothing,
    and C1 reports honestly.
  - **Benefit:** the ERL now carries **zero authorization semantics**, which removes the
    INV-17 tension the closed design carried, and removes an availability regression — a
    missing projection can no longer block a direct-`entity_id` write.
- **D-ER-2 — rewritten during ratification: input shape, not operation type.** As drafted
  (inherited from the 2026-07-14 record §3.C) D-ER-2 declared a **read/write asymmetry** —
  "a resolution miss fails closed on writes, passes through on reads". The operator identified
  that this **contradicts D-ER-9**, and it does: that phrasing belonged to the **rejected**
  closed-lookup design, in which an unmodelled id counted as a "miss". Under D-ER-9 an
  unmodelled id is **not a miss** — it is a valid id and it passes through. Ratified wording
  (spec §3.3):
  - a **natural-language miss fails closed** — `unknown_entity`, **no HTTP call** — on **both**
    reads and writes, for the mechanical reason that there is no valid id to send;
  - a **syntactically valid `entity_id` continues directly to HA exactly as today** on both
    paths;
  - **ER-1 changes only the reporting layer** (C1).

  **There is no read/write asymmetry in the resolution policy.** The two paths differ only
  because *Home Assistant* behaves differently: reads were already honest (404 →
  `not_found`); writes were not (200 + empty list claimed as success), which is precisely
  what C1 corrects. The 2026-07-14 record is **not rewritten**; this is the correction.
- **ER-1-C1 — after-only verification (operator-ratified).** A pre-read that would suppress
  the POST for a non-existent entity was **considered and rejected**: it introduces a new
  condition under which a write is not issued, which belongs to the D-ER-9 deferred decision.
  **ER-1 must not change when a POST is issued — only what the tool claims afterwards.**
  Because there is no before-state, `state_changed` is never reported, so the empty-list
  ambiguity C1 targets is never entered.
- **D-ER-10 — closed expected-state map.** C1 as originally written was under-specified: for
  most services the expected end-state is not deducible, so "verify" was undefined. Ratified
  map: `turn_on→on`, `turn_off→off`, `open_cover→open`, `close_cover→closed`; everything else
  returns `applied_unverified`. Safe against G-ER-7 because **no non-switch service has ever
  succeeded** in the evidence (`cover.close`→`ha_error`, `script.*`→`ha_error`,
  `automation.trigger`→non-existent id). `toggle` deferred (needs a before-state).
- **D-ER-7 — `ARTIFACT_VERSION` stays 1.** `_evaluator/engine.py` pins
  `SUPPORTED_ARTIFACT_VERSIONS = (1,)` and raises `ArtifactError`; `bin/aurora-context`
  **catches** it and fails soft to `Home State: Unavailable`. A version bump would therefore
  **not fail loudly** — it would silently degrade home awareness nightly and quietly undo the
  WM-6 / G-F5-04 closure. The `resolution` key is additive; ER-1 stays outside the awareness
  path.
- **D-ER-5 — emitter split.** The loader emits the registry into the artifact (pure, in-tree);
  a consumer-side `bin/emit-entity-projection` derives `aurora-entities.json`. Writes into
  `ai-stack/aurora/` stay owned by the consumer side, matching `bin/aurora-context`.

## 5. Gates

**G-ER-1…7** (spec §6). Two are operator additions to the 2026-07-14 sketch:

- **G-ER-6 — projection failure rehearsal** (the G-D6 discipline): the tools gain a new
  runtime dependency; its failure is rehearsed, not assumed.
- **G-ER-7 — backward compatibility**: every operation that already works today with real HA
  entity_ids must behave equivalently before and after ER-1. Corpus enumerated from real audit
  evidence (spec §6.1), with intentional changes listed explicitly.

**G-ER-3b was restated during ratification.** The original sketch's acceptance ("fail closed,
zero HTTP calls") is **unachievable under D-ER-9** — every historical invented id is
syntactically valid and must pass through. The ratified acceptance is stronger and is about
the **claim, not the request**: *historical unverified writes must never again be reported as
successful* — each must now produce an honest `verified` or `applied_unverified` result.

**Execution constraints of record:**

1. The **v0.1.0 baseline must be captured before the cutover** (ER-1.4a step 0) — equivalence
   cannot be demonstrated against a version already replaced.
2. The printer gates (G-ER-4 / G-ER-7) must run **outside `00:00–06:00 Europe/Madrid`**: they
   actuate `switch.impresora_3d`, and inside the `overnight` window a powered printer trips a
   real `printer_on_overnight` token (`_schema/windows.md`), polluting F-4's accruing digest
   evidence. Baseline `off` restored per the G-5 pattern.
