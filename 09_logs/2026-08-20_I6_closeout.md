## 1. What closed

I-6 replaced the D-1.5 anchor's **survival by accident** with a **mechanism**. Before I-6 the
anchor was tagged `nightly` like every ordinary snapshot and was fully in scope for the nightly
`restic forget --tag nightly`; it survived only because retention runs `--dry-run` and because
it sat in a dated legacy group no future snapshot could join. Both are coincidences, not
protection — precisely the trap the I-4 closeout named: *never rely on group shape for
protection.*

**Mechanism — Decision B (operator-approved, 2026-08-19): snapshot-level protection.** The
anchor leaves the `nightly` retention scope and carries dedicated anchor tags. Protection now
lives **in the snapshot**, so no `forget --tag nightly` — scripted, ad-hoc, or from a future
session — can reach it. This satisfies `PROJECT_RULES.md` → *Recovery Artifacts* rule 2: inert
**by construction**, not by convention.

**The backup script was deliberately NOT modified.** No `--keep-tag` was added, because that
form of protection lives in the *invocation* and fails the moment an invocation omits it.
Consequently **I-8's tracking target is unchanged at sha256 `330df064…5895a554`.**

### The identity change

```
63c072f47e532e0bb4e411522163720e8217c1311beb486bf9abce88de75aacc   (63c072f4, tags: nightly)
                              ↓  restic tag --set anchor,d15-rollback     2026-08-19
42506e442780fb99702b6f3e2a7af0c01a858cf0600db455d2dcd1160e5da5ca   (42506e44, tags: anchor,d15-rollback)
                                 original: 63c072f47e532e0b…de75aacc
```

**`42506e44` is the live protected anchor.** **`63c072f4` no longer names any snapshot** — it
survives as that snapshot's `original` provenance field, where it remains permanently
resolvable. Every historical document that references `63c072f4` therefore stays traceable;
none of them is rewritten.

**`restic` offers no ID-preserving protection mechanism.** `forget` has no exclude-by-ID and
there is no immutability flag, so every real option routes through `restic tag`, which replaces
the snapshot rather than modifying it. This was characterized on a disposable repository before
the production command was proposed, and the identity cost was stated and accepted in advance
rather than discovered afterwards. **The roadmap's original "Low complexity" rating for I-6 did
not anticipate it.**

## 4. The accidental second invocation — a no-op, not a second retag

The approved command was run **twice**. The second run reported:

```
Ignoring "63c072f4": no matching ID found for prefix "63c072f4"
no snapshots were modified
```

**Recorded as a no-op**, and provable from the data rather than only from the message: no live
snapshot ID carries the prefix `63c072f4`, so the second run was **structurally incapable** of
modifying anything. Exactly one snapshot in the repository carries an `original` field.

**This must not be generalized into a safety property of `restic tag`.** The precise statement,
per operator direction:

* repeating the command with the **historical** ID `63c072f4` was a no-op **because that ID
  stopped resolving the instant the first retag succeeded**;
* repeating a tag operation against the **new live** ID `42506e44` **would modify the snapshot
  again and produce a further ID**.

**Operational consequence to carry forward: never run `restic tag` against `42506e44`.**

## 5. Finding — the `4f4177e8` observation, refined and its wording corrected

A hypothesis raised during this work was **tested and refuted**, and the underlying observation
came out **stronger**, not resolved.

**Hypothesis:** the anchor's dangling `parent: 4f4177e8…` was the signature of a prior
`restic tag`, which would mean no snapshot was ever deleted.

**Refuted on real data:** **zero** snapshots carried an `original` field before I-6, so nothing
in this repository had ever been retagged. `5a5eadf2` has no `original` and no parent at all.

**What the evidence does support.** `4f4177e8` must have **existed at 2026-06-17 16:19**,
because restic selected it as the anchor's parent, and parent selection requires a matching
host and path set — so it was a **third member of the 2026-06-17 12-path group**. It is gone,
and not by retagging, and not by the nightly policy, which was structurally inert throughout
and has never removed a snapshot. Exactly **one** dangling parent exists repository-wide, now
inherited verbatim by `42506e44`.

**Correction to a live document.** `CURRENT_STATE.md` phrased this as *"something removed a
snapshot **on or before** 2026-06-17"*. The parent existed at 16:19 on that date, so the
removal must have occurred **after 2026-06-17 16:19**. Corrected in the triad by this closeout.

**Scope boundary, stated plainly: I-6 makes no claim against that unknown mechanism.**
Tag-based protection stops a `forget --tag nightly`; it would not necessarily have stopped
whatever removed `4f4177e8`. I-6 protects the anchor from the **normal nightly retention
path**, which is what it was scoped to do. *"The policy deletes nothing"* is not the same
statement as *"nothing deletes snapshots"*, and this repository holds evidence for the
distinction.

## 9. Rollback

Available and **not recommended** — every gate passed and the protection is correct.

```bash
restic tag --set nightly 42506e44
```

**Rollback is behavioural, not identity-restoring.** It returns the snapshot to `--tag nightly`
scope but produces a **third** ID; it cannot restore `63c072f4`, because `original` is now part
of the snapshot JSON and the content hash can never match the original again. Proven on a
disposable repository. **Data is never at risk in either direction** — the tree is preserved
and `restic check` stays clean.
